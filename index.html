Three things Linux doesn't have yet

Starling is free software, built in the open, and these are the parts worth taking seriously — whether you run it, read it, or borrow from it.

One program, not a stack of projects

The renderer, the UI framework, the window manager, the compositor and an X server are a single codebase. Anything that spans two of them is a change, not a negotiation across five upstreams.

Drawn like a game, not a web page

Every pixel goes through a GPU scene graph, from compiled machine code, with no interpreter and no virtual machine in the loop. Effects are shaders — real optics, not a blur filter over a screenshot.

Compatibility as a requirement

Wayland and X11 are both native, at the same time, on the same GPU path. Chrome, Slack, Zoom and every Electron app just run. No session picker, no XWayland caveats, no "works except".

Performance

Effects are shaders, not CSS filters

The desktop has no web stack in it at all. That isn't purism — it's what makes the rest of this section possible.

Real glass, computed per pixel

The dock and panels don't fake depth with a blur. A fragment shader gives each panel real thickness, derives a surface normal from it, and bends the view ray through that normal with Snell's law — then adds a Fresnel rim and a specular highlight riding the same surface.

Look at the text passing behind the dock: it doesn't just blur, it bends and compresses toward the rounded ends, the way it would through a real piece of glass. A blur filter cannot do that, at any performance budget.

Physically-based · GPU fragment shader

No interpreter under your session

The UI framework is compiled ahead of time to machine code and binds only a stable C rendering core. Nothing about the desktop waits on a garbage collector or a JIT to decide when your window moves.

Swift, compiled · straight to DRM/KMS

Your app's pixels are never copied

Client buffers are shared straight off the GPU and composited in place — no copy, no readback, no stream. Each app is still its own process, so a crash takes one window and nothing else.

Compatibility

App compatibility is a must,
not a choice

Nobody sits down to use a desktop. You sit down to use Chrome, Zoom, a terminal, an editor — and a desktop that can't carry them is a demo, whatever else it gets right. So compatibility here isn't a roadmap item to reach later. It's the constraint everything else was built around.

Both display servers live inside Starling. Chrome is a Wayland client; Zoom is an X11 one. They sit on the same desktop, in the same scene, on the same GPU path — sharing memory, never copied, never streamed. You don't pick a session type at login, and X11 apps keep the things X11 is still good at, like grabbing the whole screen to record without a portal in the way.

When Zoom needed X11, the desktop grew its own X server. That's the practical difference owning every layer makes.

It cuts the other way too. If your idea needs the desktop to do something no desktop does today, there's no upstream queue to join — the compositor, the framework and the protocol servers are all in reach, under one licence, in one tree.

Built in

The things other desktops bolt on

None of this is a plugin, an extension or a fork. It's what you get when the whole desktop is one application with one view of the world. Every screenshot below is the real thing, captured from a running session.

Tiling and floating, both first-class

Floating windows by default. Flip one switch and everything arranges itself master-and-stack, the way a tiling window manager does — your browser holding the master pane, everything else stacked beside it.

Flip it back and every window returns to exactly where it was floating. No extension, no separate desktop to switch to, nothing to relearn.

Settings → Appearance → Tiling Windows

Spaces and Mission Control

Slide between virtual desktops, carry a window along as you go, or pull back with one key and see every space at once. Anything you send fullscreen quietly becomes a space of its own.

Drag a window between spaces from the overview, or add a new one from the strip along the top.

Ctrl + ↑ for the overview · Ctrl + ← → to switch

Monitors that behave

Every display gets its own menu bar, its own wallpaper and its own spaces — but they are one desktop, not two. Park a window across the boundary and it just works: half drawn on one screen, half on the other, at each screen's own scale.

Unplug a monitor and its windows come home instead of vanishing off into nowhere. Plug it back in and the desktop picks up where it left off.

Hot-plug · per-display scale · per-display spaces

And a full set of apps, in the same framework

Files, Terminal, Settings, Calculator, Text Editor, Image Viewer and an App Store that installs from the Ubuntu archive — each one written in the same framework as the shell that hosts it, and each one its own process. One theme change reaches all of them at once, because there's no toolkit boundary for it to stop at.

Install

One package, then pick Starling at login

# Ubuntu 25.10 or 26.04, amd64. Starling needs a Wayland-capable login
# manager. Ubuntu Desktop already has one (GDM); on Server or a minimal
# install, add it first:
sudo apt install gdm3

# Install Starling and its runtime dependencies:
sudo apt install ./starling-desktop_0.1-1_amd64.deb

# Log out (or reboot). At the login screen click your name, open the
# session menu (the gear / lower-corner button), pick "Starling", sign in.
This is an early preview. Starling runs a real desktop on real hardware today, but it is version 0.1: expect rough edges, missing settings, and apps that still need work. Verified on AMD graphics under Ubuntu 25.10 and a fresh Ubuntu 26.04. The package pulls in a login manager if you don't already have one.
